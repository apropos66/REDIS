# REDIS

A tiny Redis-style, in-memory key-value store server, written from scratch in C.

*An educational clone, not affiliated with or endorsed by the Redis project.*

> **Note:** This README was generated by AI (Claude). The project itself is a hands-on learning exercise: the C code was typed out, debugged, and wrestled with by hand while learning how computers, memory, and networks actually work.

**Status:** version 1 (v1) complete.

## What it is

This project is a server that keeps key-value pairs in RAM. Clients connect over TCP, send a plain-text command, and get a text reply back. The whole thing uses only the C standard library and the POSIX sockets API. There are no external dependencies.

## Features (v1)

- Hash table with separate chaining (djb2 hash, 13 buckets)
- Text commands: `SET`, `GET`, `DEL`
- Command parser with basic error replies (wrong argument count, unknown command, missing key)
- TCP server on port **6380**
- The store owns its own copies of keys and values (no dangling pointers into client buffers)
- Built and tested with AddressSanitizer and UBSan (`-fsanitize=address,undefined`)

## Commands

| Command | What it does |
|---|---|
| `SET key value` | Stores `value` under `key`. Overwrites the old value if the key already exists. |
| `GET key` | Returns the value stored under `key`, or an error reply if it doesn't exist. |
| `DEL key` | Deletes `key`. Replies with an error if it doesn't exist. |

Commands are split on whitespace, so keys and values can't contain spaces yet.

## Build

```sh
gcc -Wall -Wextra -fsanitize=address,undefined -g main.c parse.c store.c -o main
```


## Run

Start the server:

```sh
./main
```

In another terminal, connect with `nc` (netcat) and type commands:

```sh
nc localhost 6380
SET name Ali
GET name
DEL name
```

Note that the real `redis-cli` won't work with this server, because this server speaks a simplified plain-text protocol rather than Redis's RESP.

## How it's organized

```
client (nc) ──TCP──▶ main.c   network layer: socket, bind, listen, accept, read, write
                      │
                      ▼
                    parse.c   command parser: split a line, pick the command, build a reply
                      │
                      ▼
                    store.c   storage: hash table with chaining (set / get / del)
```

Each layer only knows about the one below it. The parser knows nothing about sockets, and the store knows nothing about commands, so each part can be tested on its own.

## Known limitations

- **One client at a time.** A second client waits until the first one disconnects.
- **No line framing.** The server assumes one `read` is one complete command. TCP doesn't guarantee that, so a command split across packets (or two commands in one packet) is mishandled.
- **No spaces in values**, and no quoting.
- **Fixed number of buckets.** The table never resizes, so lookups slow down with very large numbers of keys.
- **No persistence or expiry.** Everything is lost when the server stops.
- **No authentication.** For learning and local use only.

## Roadmap

1. Line framing: buffer incoming bytes and only parse complete lines
2. Many clients at once with an event loop (`poll`)
3. Key expiry
4. Saving to disk and loading at startup
5. Table resizing
